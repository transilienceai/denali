01 / Executive summary

AI security built around evidence, not assumptions

Denali helps security, cloud, application, and AI governance teams understand which AI systems exist, how they are deployed, which enterprise AI applications are being used, what identities and capabilities they rely on, which weaknesses are supported by evidence, and where runtime behavior requires attention.

01

Discover the estate

Build a normalized AI inventory across source repositories, cloud resources, applications, identities, models, tools, data stores, workloads, and software components.

02

Connect code to runtime

Correlate immutable source declarations with independently observed cloud workloads using exact deployment identifiers—not names or fuzzy similarity.

03

Prioritize explainably

Combine findings, vulnerabilities, proven relationships, and runtime detections into deterministic issues that retain every supporting fact and coverage limit.

✓
Core proposition

Denali separates inventory, findings, vulnerabilities, runtime activity, detections, issues, and coverage. A healthy connection proves access—not collection. A missing signal never becomes a reassuring zero. This creates a defensible evidence trail for security decisions, governance reviews, and customer assurance.

↗
Latest production update

Azure Repos is now a separate read-only connection with one-time delegated repository selection, app-only steady-state access, immutable revision binding, bounded source analysis, and eligible code-to-cloud correlation. Google Workspace provides a keyless connection for bounded Gemini and AI-related OAuth audit evidence. Healthy provider validation automatically starts durable evidence collection; cloud collection refreshes dependent source correlation and rule evaluation. Deployment workflows can also submit matching Syft and Grype evidence through GitHub OIDC without a Denali API key, while a secure administrator upload remains available as a recovery path. The connection experience exposes setup progress, per-plane validation, evidence readiness, and background collection status.

How to read maturity

“Production observed” records the successful setup, consent, validation, or collection step explicitly exercised so far; it is not a claim that every lifecycle edge case has passed. Full provider acceptance still requires create, setup or callback, validation, collection, disable, and delete evidence. Coverage remains independent: a healthy connection proves access, while a complete collection proves only the declared plane and bounded window.

04 / Use cases

From board-level governance to engineering investigation

Denali supports complementary workflows across security leadership, cloud security, AppSec, SOC, platform engineering, and AI governance.

01

Enterprise AI inventory and AI-BOM

Establish a defensible baseline of AI systems across code, cloud, SaaS applications, models, tools, identities, data dependencies, and software components.

  • Identify new, changed, unreviewed, or withdrawn assets.
  • Trace every asset to its source, scope, and observation time.
  • Support governance attestation and architecture review.
Outcome: a living, evidence-backed register rather than a manually maintained spreadsheet.
02

Code-to-cloud ownership and lineage

Answer which repository produced or declares a workload, which identity runs it, which model it targets, and which tools or data actions it can perform.

  • Resolve exact deployment identifiers across AWS, Azure, GCP, and Kubernetes.
  • Keep unproven or ambiguous links visible without asserting them.
  • Give cloud and application teams a shared investigation view.
Outcome: faster ownership, impact analysis, and remediation routing.
03

AI posture and software supply-chain risk

Combine AI-specific configuration conditions with SBOM and vulnerability evidence for the exact deployed artifact.

  • Inspect atomic findings before accepting a higher-order risk conclusion.
  • Prioritize fixable vulnerabilities in deployed AI workloads.
  • Preserve scanner disagreement, fix status, and coverage.
Outcome: fewer generic alerts and clearer, evidence-linked remediation decisions.
04

Attack-path and issue prioritization

Surface security consequences only when the required findings and capability relationships are independently supported.

  • Show the path across workload, identity, model, tool, and data.
  • Explain why the issue exists and what evidence is missing.
  • Track lifecycle without erasing historical observations.
Outcome: explainable prioritization that can withstand technical and audit review.
05

Runtime monitoring and investigation

Normalize provider audit metadata and detect narrow patterns such as repeated AI app sign-in failures, consent changes, or use of an unreviewed model.

  • Correlate activity to exact independently inventoried entities.
  • Keep unresolved actors and resources visible for investigation.
  • Retain event evidence without collecting prompt or response content.
Outcome: AI-specific operational context for SOC and cloud security teams.
06

AI application discovery and consent review

Identify enterprise AI applications in Microsoft Entra and Google Workspace, then evaluate permissions or observed activity without prematurely labelling them “shadow AI.”

  • Review Entra app identity, publisher, grants, roles, sign-ins, and administrative changes.
  • Review Workspace Gemini feature use and catalog-matched AI OAuth application events within the collected audit window.
  • Apply explicit approved, unreviewed, or unwanted governance while keeping catalog match, observed use, and confirmed risk separate.
Outcome: a cross-platform SaaS AI governance workflow with honest evidence and coverage boundaries.
07

Multi-tenant security service delivery

Operate isolated customer or business-unit workspaces using Clerk Organizations mapped to internal tenant UUIDs and server-side authorization.

  • Read access for members; mutations limited to administrators.
  • Tenant-scoped database queries and provider callbacks.
  • Same-origin browser-to-API routing; secrets never reach the browser.
Outcome: a controlled hosted multi-tenant foundation for managed or enterprise delivery.
08

Evidence consolidation and assurance

Bring cloud observations, source analysis, enterprise AI application evidence, OCSF findings, SBOMs, vulnerabilities, and runtime events into a consistent investigation model.

  • Preserve original source identity and bounded evidence locators.
  • Distinguish observed facts from inferred security conclusions.
  • Expose coverage gaps before interpreting counts or trends.
Outcome: one defensible evidence model across fragmented AI security signals.

✓

Keyless customer access

AWS assume-role, Azure and Entra consent/RBAC, GCP workload identity, Google Workspace domain-wide delegation, and GitHub App installation replace uploaded access keys and personal tokens.

✓

Server-side tenant resolution

The API derives the Denali tenant from the verified active Clerk Organization. Client-supplied tenant identifiers never select customer data.

✓

Secrets stay backend-only

Database, Clerk backend, and provider secrets live in Modal Secrets. Vercel receives only the public Clerk publishable key and Modal routing origin.

✓

Bounded evidence retention

Denali retains normalized metadata and evidence needed for explanation—not raw prompts, responses, tokens, secrets, private keys, caller IPs, or unbounded payloads.

✓

Durable background work

Hosted validation, provider collection, and vulnerability imports use PostgreSQL job records, leases, bounded terminal states, and Modal workers that receive durable identifiers only.

✓

Explicit lifecycle safeguards

Connections validate declared read planes independently, can be disabled before deletion, and preserve previously collected evidence after configuration removal.

06 / Differentiation

What makes Denali different

Denali is designed as an independent AI security product—not a re-skinned CSPM and not a generic log viewer.

ObserveInventory & activity

Record provider and repository facts with source identity.

CorrelateExact relationships

Join only independently supported identifiers.

EvaluateFindings & detections

Apply deterministic rules with explicit coverage.

PrioritizeIssues & paths

Compose sufficient evidence into explainable consequences.

01Evidence before verdicts. Similar names do not prove identity, deployment, ownership, use, or risk.
02Coverage before counts. Partial, failed, unsupported, and unknown remain visible.
03Source and runtime stay independent. A code declaration is not execution evidence.
04Open ecosystem. PostgreSQL-backed, Apache 2.0 open source, and compatible with OCSF, Syft, Grype, and Prowler inputs.
05Customer-controlled access. Provider grants are read-only, scoped, reviewable, and revocable at the source.
06No silent content collection. Prompt/response telemetry requires a separate policy, consent, permission, redaction, and retention decision.

08 / Evaluation

A practical customer evaluation path

A focused proof of value can start with a deliberately bounded set of repositories, cloud accounts, projects or subscriptions, enterprise application directories, and runtime audit sources.

Phase 1

Scope & connect

Agree success criteria, evidence boundaries, provider scopes, and data-retention expectations. Configure read-only connections.

Phase 2

Discover & correlate

Collect a bounded AI inventory and prove selected repository-to-workload relationships with exact identifiers.

Phase 3

Assess & observe

Collect posture and runtime metadata; submit exact-artifact SBOM and vulnerability evidence; evaluate detections and evidence-backed issues.

Phase 4

Review & decide

Validate coverage, review findings and paths with owners, document outcomes, gaps, and the production adoption plan.

Risk explainability

Access minimization

Operational fit

Important acceptance principle

Provider onboarding is accepted only after a real create, setup/callback, validation, disable, and delete pass. Collection is tested separately. Mocks and a healthy badge demonstrate contracts and access—they do not prove that customer inventory exists or that risk is absent.

Recommended next step

Select one high-value AI application for an evidence-backed evaluation.

Start with a repository, its corresponding cloud workload, execution identity, model, and one posture or runtime source. This produces a concrete source-to-runtime story while keeping permissions and evidence scope small and reviewable.
